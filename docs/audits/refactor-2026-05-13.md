# Refactor Notes — 2026-05-13

This document explains the changes made to the codebase based on the two audits in this folder. For each change, it answers: **what was wrong**, **why the fix is better**, and **the general principle to carry forward**.

---

## Part 1 — LLM Provider Factory

### What changed

GEIA (a proxy at `api.saia.ai`) was removed as the single hardcoded LLM provider. The system now has a factory pattern where the provider (`openai` or `anthropic`) is selected at runtime via a `LLM_PROVIDER` environment variable.

**Python** (`model_factory.py`): The factory already existed with three branches — GEIA, OpenAI, and Anthropic. Removing GEIA left a clean two-provider factory. Adding a new provider means implementing one method (`_create_<provider>_model()`) and registering it in the `create_model()` switch.

**TypeScript** (`llm-factory.ts`): Created a new file with a `createLLMClient(config)` function. Currently only OpenAI is supported — Anthropic would need `@anthropic-ai/sdk` and a rewrite of the tool-calling loop (the OpenAI and Anthropic APIs have different shapes for tool use).

### Why it matters

Using a proxy (GEIA) as the only provider couples the entire system to a single third-party intermediary. If the proxy goes down, changes its API, or raises prices, the system breaks completely with no alternative. The factory pattern gives you:

1. **Substitutability** — swap providers without touching business logic
2. **Cost control** — run the same code against cheaper/faster models by changing one env var
3. **Testability** — inject a mock or local model in tests without modifying source

### The general principle

**Depend on abstractions, not concrete providers.** Any LLM call site should receive a model object (or model configuration) from outside — not create one internally with hardcoded credentials or URLs. This is the same reason you don't hardcode a database connection string in application code; you read it from config.

The factory pattern also makes the "supported providers" explicit. There's one place to add, change, or remove a provider — not a dozen `if GEIA_API_KEY` checks scattered across files.

## Part 2 — Architecture Audit Fixes

### Finding 1 — Article Scorer: LLM replaced with embeddings

**What was wrong:** The article scorer sent articles to an LLM in batches of 15, asking it to rate each 1–5 for relevance. For a `pro` tier request with many articles, this meant 5–15 extra LLM API calls per research run — each taking 3–8 seconds and burning tokens.

The LLM was also generating a `brief_reason` field per article that was immediately discarded — roughly 200–400 wasted output tokens per batch.

**Why the fix is better:** Relevance scoring (how related is article X to query Y?) is a semantic similarity task. Semantic similarity is exactly what sentence-transformer embeddings were designed for. The `all-MiniLM-L6-v2` model was already loaded in the codebase for the clustering node — using it here costs nothing extra.

```python
# Before: 1 LLM call per 15 articles (~3-8s per call)
scores = _score_batch(llm, batch, context_text, ...)

# After: local embedding cosine similarity (~50ms total)
query_emb = model.encode([context_text])
article_embs = model.encode(article_texts)
scores = cosine_similarity(query_emb, article_embs)[0]
```

The result is the same — articles ranked by relevance — but the approach matches the tool to the task. An LLM is a reasoning engine; it should not be doing arithmetic that a distance metric can handle.

**The general principle:** Ask yourself what kind of task you actually have before reaching for an LLM:

| Task type | Right tool |
|---|---|
| Semantic similarity / ranking | Embeddings + cosine similarity |
| Classification with fixed labels | Fine-tuned classifier or embeddings |
| Extraction from structured text | Regex or a parser |
| Open-ended reasoning, synthesis | LLM |
| Report generation from templates | Jinja2 / string formatting |

LLMs are expensive, slow, and non-deterministic. Use them only where their reasoning capability is genuinely needed. Every time you replace an LLM call with a deterministic function, you get: lower cost, lower latency, and reproducible behavior.

### Finding 2 — Buyer Agent: Two-Model Strategy

**What was wrong:** The buyer agent used `gemini-2.5-pro` (the most expensive model) for every turn of its tool-calling loop — including turns where the agent just calls `list_tiers` (returns static JSON) or `check_budget` (passes a tier name to a deterministic function). A capable reasoning model was paying the full price for work that required zero reasoning.

A typical 5-turn run:
- Turn 1: call `list_tiers` — no reasoning needed
- Turn 2: pick a tier from the list — one-word decision
- Turn 3: call `check_budget` — pass a tier name
- Turn 4: call `purchase_research` — assemble a query string
- Turn 5: summarize the research result — **this is where a capable model matters**

**Why the fix is better:** The fix adds a second, cheaper model (`gpt-4o-mini`) for turns 1–4 and switches to the strong model (`gpt-4o`) only after a successful purchase is confirmed:

```typescript
const isPurchased = messages.some(
  m => m.role === "tool" && m.content.includes('"success":true')
);
const model = isPurchased ? config.BUYER_LLM_MODEL : config.BUYER_LLM_MODEL_FAST;
```

For a typical 5-turn run, ~80% of agent LLM cost is eliminated. The user sees identical output because the final summarization — the turn that benefits from reasoning capacity — still uses the strong model.

**The general principle:** In multi-turn agent loops, model capacity requirements are not uniform across turns. Tool-routing turns (deciding which function to call) need significantly less reasoning than synthesis turns (interpreting results and forming a response). The pattern to apply:

- **Fast/cheap model** for tool dispatch, format conversion, simple decisions
- **Capable model** for synthesis, novel reasoning, or when quality matters to the user

This is called **model cascading** or **two-model tiering**. The research engine already applied this correctly in `research_analyzer.py` (Flash for event extraction, Pro for synthesis). The buyer agent was the gap.

### Finding 3 — Context Parser: Eliminate Redundant LLM Fields

**What was wrong:** The context parser called an LLM to extract 5 fields: `query_intent`, `metric_direction`, `key_entities`, `metric_magnitude`, and `suggested_event_types`. Two of those five were already available without an LLM:

1. **`metric_direction`** — whether a metric "dropped" or "increased" — is entirely keyword-matchable. A regex pattern handles it in 1ms.
2. **`key_entities`** — the parser already called `_extract_topics_and_entities()` earlier in the same function. The LLM was re-extracting the same entities at extra cost.

**Why the fix is better:** Regex is deterministic, instantaneous, and free. For a factual extraction task with finite outcomes (decrease / increase / volatile / unknown), it is strictly better than an LLM call:

```python
_DECREASE_RE = re.compile(r"\b(drop|drops|dropped|fell|declin|crash|...)\b", re.I)

def _infer_metric_direction(text: str) -> str:
    if _DECREASE_RE.search(text): return "decrease"
    if _INCREASE_RE.search(text): return "increase"
    ...
    return "unknown"
```

The LLM prompt was also narrowed from 5 requested fields to 3 — cutting output tokens by ~40% per context-parser call.

**The general principle:** Before adding a field to an LLM prompt, ask: can this be computed without the LLM? Common cases where LLMs are overkill:

- **Keyword matching** → regex
- **Numeric extraction** → regex or `float(re.search(r"[\d.]+", text).group())`
- **Deduplication** → set operations
- **Field already computed elsewhere in the same pipeline** → pass it through

Also: LLM prompts should be minimal. Every field you ask for is output tokens you pay for. If you don't use a field downstream, remove it from the prompt immediately.

### Finding 4 — Request Cache in runner.py

**What was wrong:** Every call to `run_engine()` re-ran the entire 7-node pipeline from scratch, including 3–5 LLM calls, multiple Tavily API searches, and embedding inference. Repeating the same query (same topic, dates, tier) would re-run everything and produce a slightly different (non-deterministic) result.

**Why the fix is better:** A simple in-memory dict cache keyed on `MD5(query + start_date + end_date + tier)` makes repeated identical requests instant:

```python
key = _cache_key(req.query, req.start_date, req.end_date, req.tier)
if key in _result_cache:
    return _result_cache[key]
```

The cache key deliberately excludes `request_id` — two requests with identical content should return the same result. Only completed (non-failed) results are cached, so errors are not frozen in.

**The general principle:** Cache at the coarsest meaningful granularity. The right cache boundary for an LLM pipeline is the full pipeline output, not individual LLM calls. Caching individual LLM calls is complex (you need to handle partial state) and usually not worth it. Caching the final result of the entire pipeline is one dict lookup.

For production: replace the in-memory dict with Redis or a persistent store so the cache survives restarts. The key structure (`MD5(inputs)`) stays the same.

## Part 3 — Eval & Observability

### Why eval is non-negotiable for LLM systems

Functional tests (unit tests, integration tests) verify that code runs correctly: a function returns the right type, an HTTP endpoint returns 200, a schema validates. They cannot tell you whether the LLM output is any good.

Without eval tooling:
- A prompt change that improves one case and breaks ten others is undetectable before shipping
- You cannot measure whether a code change improved or degraded quality
- "It looked fine when I ran it" is the entire QA process

The three components added here address this:

---

### Component 1 — LangSmith Tracing

LangSmith automatically instruments LangGraph when two environment variables are set:

```
LANGCHAIN_TRACING_V2=true
LANGCHAIN_API_KEY=ls__...
```

This gives you a per-request trace showing: which node ran, how long it took, what the LLM was sent, what it returned, and token counts. For the buyer agent, `wrapOpenAI` adds the same visibility to the TypeScript tool-calling loop.

**What you learn from traces that you can't see from logs:**
- Which node is the latency bottleneck
- Whether a prompt is producing consistent outputs or highly variable ones
- Token cost per request, per node, per model
- Whether your fast model is actually succeeding at tool routing or falling back to the strong model

**When to look at traces:** After any prompt change, after a user reports a bad result, or when you notice latency is higher than expected.

---

### Component 2 — Golden Eval Dataset (`eval_cases.jsonl`)

25 annotated cases covering the query types the system is designed to handle:

- **Easy** — simple factual queries (Aave TVL trends, Base chain growth)
- **Medium** — causal queries with a clear answer (Bitcoin ETF impact, Arbitrum post-airdrop)
- **Hard** — multi-factor causal chains (FTX collapse, UST depeg, stETH discount)
- **Out-of-scope** — queries the system shouldn't have data for (pizza recipe)

Each case records `expected_topics`, `expected_min_sources`, `expected_causal_chain`, and `difficulty`. This is the **regression anchor** — if a code change causes a previously-passing case to fail, you catch it before shipping.

**How to grow this dataset:** After every production run, add the 1–2 most interesting queries to the dataset. After a bad result, add the failing query immediately — that's the most valuable kind of case because it documents a known deficiency. Aim for 50–100 cases before running evals in CI.

---

### Component 3 — RAGAS Eval Script (`eval_ragas.py`)

RAGAS is an evaluation framework built for RAG pipelines (Retrieve → Score → Generate). It measures:

- **`answer_relevancy`** — does the answer address the question? (uses an LLM judge)
- **`faithfulness`** — are the claims in the answer supported by the retrieved sources?

These are the two metrics that matter most for a research report system: you want answers that are on-topic and grounded in sources, not hallucinated.

```python
result = evaluate(dataset, metrics=[answer_relevancy, faithfulness])
assert result["answer_relevancy"] >= 0.70
assert result["faithfulness"] >= 0.65
```

**Important caveat:** RAGAS itself uses an LLM as the judge. Running it in CI against real queries costs API credits. The CI workflow runs it only on `main` branch pushes using `EVAL_MOCK_MODE=true` (mock engine) to avoid unexpected costs. Real quality measurement requires running it against the live engine with actual API keys.

**When to run the full eval:** Before and after any prompt change. Before any model upgrade or downgrade. Before releasing a new tier configuration.

---

### Component 4 — Quality Flags on the Audit Store

The `POST /admin/flag/:id` endpoint lets you mark a specific request as having a quality problem:

```bash
curl -X POST http://localhost:8200/admin/flag/req-abc123 \
  -H "Content-Type: application/json" \
  -d '{"reason": "hallucinated a non-existent protocol event"}'
```

The `quality_flag` column in `audit.db` then provides a corpus of known-bad outputs. This is the earliest form of human-in-the-loop feedback. Over time, flagged records become candidates for the eval dataset — you found the bad output in production, you can add it as a golden case to prevent regression.

**The feedback loop:**
```
User sees bad output → Flag it via /admin/flag/:id → Review flagged record → Add to eval_cases.jsonl → Fix prompt → Run make eval → Confirm fix → Ship
```

## Summary — Mental Model for LLM Systems

The changes in this refactor reflect a consistent set of principles:

**1. Match the tool to the task.**
Embeddings for similarity, regex for pattern matching, LLMs for reasoning. Don't use a reasoning engine where a lookup table works.

**2. Tier your models by turn complexity.**
In multi-turn agents, not every turn needs the same model. Use the expensive model where it adds value; use the cheap model everywhere else.

**3. Minimize LLM prompt surface area.**
Every field you ask an LLM to produce is output tokens you pay for. If you don't use it downstream, remove it. If a cheaper method produces it accurately, use that instead.

**4. Cache pipeline outputs, not internal steps.**
The right cache boundary is the complete result of a deterministic-enough pipeline (same inputs → same-ish output). One dict lookup replaces 5 LLM calls.

**5. You cannot know if an LLM system is working without eval.**
Functional tests tell you the code runs. Eval tells you whether the output is any good. A golden dataset + RAGAS metrics + CI is the minimum viable quality gate. Add it before the system handles real users, not after.

**6. Traces are the debugger for LLM systems.**
When something goes wrong in an LLM pipeline, you need to see what each node was sent and what it returned. LangSmith gives you that. Without it, debugging means adding print statements and re-running the whole pipeline — the equivalent of debugging without a debugger.
